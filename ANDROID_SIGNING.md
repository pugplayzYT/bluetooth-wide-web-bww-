# Android signing and updates

Official APKs are release builds signed with a stable private key. Android compares the signing certificate, application ID and versionCode when installing an update. Open source code does not expose the key: GitHub Actions receives it only through encrypted repository secrets, during trusted main-branch release builds. Pull requests build and test independently with a developer debug key and never receive the release secrets.

## Existing installations

The official certificate is pinned in `android/signing-certificate.sha256`. It preserves the key used by our original downloads through Android 0.6.1, so those installations can update in place without losing accounts, drafts or website localStorage. The original private key was retained outside the repository and reprotected with a random keystore password; its public certificate remains unchanged.

The automated Android 0.6.2/0.6.3 builds previously used temporary GitHub runner debug keys. Android will reject an update signed with a different key. A new key cannot repair that mismatch; updating those installations without uninstalling requires the exact private key used for the installed APK. The retained original key does not match the current 0.6.3 download. Do not uninstall merely to troubleshoot an update: uninstalling removes BWW's phone data, including website localStorage. The signing fix prevents this problem in future official releases.

## Maintainer: configure GitHub Actions once

Keep the private signing bundle outside any Git checkout. It contains `bww-release.p12`, `credentials.json` and the public `certificate.sha256`. Keep an offline backup; losing the private key prevents compatible future updates. Never upload the bundle to the repository, a release, build artifacts or chat. `.gitignore` excludes common keystore filenames, but that does not protect a JSON password file stored inside a checkout.

Install Python 3.10+, a JDK providing `keytool`, and GitHub CLI. Sign into GitHub CLI on your own computer with `gh auth login`. Extract the private bundle, open a terminal there, and run:

```powershell
py -3 configure_android_signing.py --bundle . --repo pugplayzYT/bluetooth-wide-web-bww-
```

This verifies the bundle's public certificate and sends the four values to GitHub with standard input, without printing secret values or putting them in command history:

| Actions repository secret | Contents |
| --- | --- |
| `BWW_ANDROID_KEYSTORE_BASE64` | Base64-encoded private keystore |
| `BWW_ANDROID_STORE_PASSWORD` | Keystore password |
| `BWW_ANDROID_KEY_ALIAS` | Key alias |
| `BWW_ANDROID_KEY_PASSWORD` | Key password |

The secrets appear under **Settings → Secrets and variables → Actions**. No environment approval is required by this workflow. Run **Actions → Build and test → Run workflow** after configuring them. A missing key or unexpected certificate fails release publication instead of falling back to a new debug key. Repository maintainers able to alter trusted workflow code must be trusted with release signing; review workflow changes accordingly.

The CI helper decodes the keystore into a private temporary directory, removes it after building, and verifies the APK's public certificate. Only signed APKs are packaged; private key files and passwords are excluded from upload artifacts.

## Build it yourself

A normal development build needs no official secret:

```powershell
cd android
.\gradlew.bat assembleDebug
```

Gradle uses your own local debug key. Development builds use `dev.bww.dev`, so they can coexist with the official `dev.bww` app and have separate data.

For your own release, create a keystore outside the repository:

```powershell
keytool -genkeypair -keystore C:\Private\my-bww.jks -alias my-bww -keyalg RSA -keysize 3072 -validity 10000
```

Provide `BWW_ANDROID_KEYSTORE` (absolute path), `BWW_ANDROID_STORE_PASSWORD`, `BWW_ANDROID_KEY_ALIAS` and `BWW_ANDROID_KEY_PASSWORD` in your local build environment, then run `assembleRelease`. Keep your own key stable for your users. Your release cannot update an official installation signed by someone else's key. Fork maintainers using the official CI helper must replace `android/signing-certificate.sha256` with their own public certificate fingerprint and configure their own repository secrets.

## Versions and downloads

Every Android app fix increases **both** versionName and versionCode. Packaging records a hash of the Android build inputs and rejects changed inputs under an already-published version. Rebuilding unchanged inputs reuses the immutable signed APK for that version, so packaging does not manufacture duplicate releases. Do not rotate the official key during ordinary version bumps.

[Latest official downloads](downloads/README.md) is regenerated by Actions after both build jobs pass. Documentation links to that page instead of a particular ZIP/APK version. The publish job verifies separate manifests and checksums, refuses overlapping packages, and skips publication if main advanced during the build. It never creates tags.

## After setup

Once all four Actions secrets are configured, future official builds use them automatically. Keep a private offline backup of `bww-release.p12` and `credentials.json` so you can restore secrets if needed. The one-time encrypted transfer and transfer helper have been removed from the current repository; they are not needed for releases. Do not add private backup files to GitHub.
